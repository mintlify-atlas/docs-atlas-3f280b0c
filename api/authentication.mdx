Every ZPan API request must be authenticated. The server supports three mechanisms: Bearer API keys for scripting and integrations, session cookies set automatically by the browser SPA, and OAuth 2.1 DPoP-bound tokens for external application integrations. Unauthenticated requests to protected endpoints return `401 Unauthorized`. Requests authenticated with valid credentials that lack the required scope return `403 Forbidden`.

## Authentication Methods

### 1. Bearer API Key

API keys are the recommended method for scripts, CI pipelines, and third-party tools. After creation, pass the key in the `Authorization` header on every request:

```
Authorization: Bearer zpk_…
```

Keys are prefixed `zpk_`. Each key is associated with a set of permission scopes that determine which endpoints it can call. A key without the required scope for an endpoint returns `403 Forbidden` even if it is otherwise valid.

**Creating an API key:**

1. Sign in to ZPan and open **Settings → API Keys**.
2. Click **Create API key**.
3. Enter a name, choose an expiry (optional), and select the scopes the key needs.
4. Copy the key immediately — it is shown only once.

<Warning>
  Store API keys securely. ZPan displays the full key value only at creation time. If you lose a key, delete it and create a new one.
</Warning>

### 2. Session Cookie

When you sign in through the ZPan web interface, the server sets an HTTP-only session cookie. The browser SPA uses this cookie automatically on every API request. You do not need to manage this cookie manually.

This method is not suitable for programmatic access from outside a browser context. Use a Bearer API key instead.

### 3. OAuth 2.1 DPoP Token

ZPan supports OAuth 2.1 with DPoP (Demonstrating Proof of Possession) for external application integrations. DPoP-bound tokens are cryptographically tied to a private key held by the client, preventing token replay.

Discover the authorization server configuration at:

```
GET /.well-known/oauth-authorization-server/api/auth
```

And the protected resource metadata at:

```
GET /.well-known/oauth-protected-resource/api
```

## Using a Bearer API Key

Include the key in the `Authorization` header of every request:

<CodeGroup>

```bash curl
curl -H 'Authorization: Bearer zpk_...' \
  https://your-zpan.example/api/objects
```

```javascript fetch
const response = await fetch('https://your-zpan.example/api/objects', {
  headers: {
    'Authorization': 'Bearer zpk_...',
  },
})
const data = await response.json()
```

</CodeGroup>

## Scope Enforcement

Every API endpoint declares the scope(s) it requires. When you create an API key you explicitly grant it a subset of available scopes. If a key calls an endpoint whose required scope is not granted, the server returns:

```json
{
  "error": {
    "code": 403,
    "message": "Forbidden",
    "status": "PERMISSION_DENIED"
  }
}
```

Common scopes follow a `resource:action` pattern, for example `objects:read`, `shares:create`, or `images:upload`. Admin-only endpoints additionally require the caller to hold the site `admin` role regardless of API key scopes.

## Error Reference

| HTTP Status | Meaning |
|---|---|
| `401 Unauthorized` | No credentials supplied, or the supplied credentials are invalid or expired. |
| `403 Forbidden` | Valid credentials, but the key lacks a required scope or the user lacks a required role. |

<Tip>
  Use the narrowest set of scopes needed for your integration. A key scoped to `objects:read` cannot create or delete files even if it is stolen.
</Tip>
